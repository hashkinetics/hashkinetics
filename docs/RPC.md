# HashKinetics JSON-RPC — the complete reference (node v0.19.7 — 26 methods)

**Every method the node answers (26 as of v0.19.7, 2026-10-08 — no method was added by R18; the `hk_submitTx` refusals, `hk_submitBundle`'s shape rule and `activations.payword_cap_from` are what changed), with parameters, result shapes, limits and the errors you can get.** The public endpoint is `https://rpc.hashkinetics.org` (testnet-1, `hashkinetics-1-4e4ea68d`); a local node answers on `http://127.0.0.1:26000`. This is the same API the website, the explorer, the faucet and the Windows wallet use — there is no second, private one. Source of truth: `chain/crates/hk-node/src/rpc.rs` (one `dispatch` match; if this page and the code disagree, the code wins and this page has a bug).

## Transport

- HTTP/1.1 **POST**, any path, body `{"method": "<name>", "params": {…}}`. The `jsonrpc`/`id` fields of JSON-RPC 2.0 are accepted and ignored; `params` may be omitted for methods that take none.
- Responses are `{"result": …}` or `{"error": "<message>"}` (HTTP 200 for a result, HTTP 400 for an `{"error"}` a method returns — the same 400 as unparseable JSON — so a client keys on the body, never on the status; HTTP 413-equivalent refusal above 8 MiB of body; `rpc.rs` `handle_conn` is the one place the status is chosen).
- **No authentication, no rate limit, CORS `*`.** Operators: keep your own node's RPC on loopback or firewalled to peers (`docs/VALIDATOR-ONBOARDING.md` §0/§4); the public endpoint sits behind a reverse proxy and Cloudflare.
- All amounts are **micro-units as decimal strings** (u128); `1.000000` = `"1000000"`. Ids, hashes and hex fields are lowercase hex without `0x`. Asset ids are 32-byte hex; the transparent test unit is `0909…09` (32 × `09`).

```bash
curl -s -X POST https://rpc.hashkinetics.org \
  -d '{"method":"hk_chainInfo","params":{}}'
```

## Chain & liveness

| Method | Params | Result |
|---|---|---|
| `hk_chainInfo` | — | `chain_id`, `genesis_digest`, `node_version` (v0.15.2: the binary answering, e.g. `v0.15.2`), `peers` (v0.15.2: live p2p peer count), `height`, `app_hash`, `signer{epoch, remaining, capacity}` (this node's own operational-key budget; observers report their own unused tree), `fee{micro, from_height, burned_micro}`, `history{disk_from, ram_window, indexed_txs, retain_blocks}` (v0.16.0: `retain_blocks` = null on an archive node, N when the node prunes segments older than tip−N), `process{rss_bytes, uptime_secs, verifier_init_ms, disk_free_bytes}` (v0.17.0 / R11: this process's resident set in bytes — Linux and macOS since v0.19.4, null elsewhere; `disk_free_bytes` = free space on the block log's filesystem (v0.19.4) — seconds since `start`, and how long the verify-only STARK client took to come up; null when no verifier is wired. The onboarding doc's RAM line is checkable with this call.), **`activations{mandate_asset_from, rotation_v2_from, payword_cap_from}` (v0.19.6 / R17; `payword_cap_from` since R18, 2026-10-08 — the release after v0.19.6): the heights at which THIS binary switches rules on this chain — `mandate_asset_from` (asset-bound mandates, testnet-1: 1,872,500), `rotation_v2_from` (chain-bound v2 rotation certificates with the `valid_from_height` freshness window; `null` = never — testnet-1 until a later patch names it, once every seat on the roll call answers v0.19.6) and `payword_cap_from` (R18: the PayWord caps as a consensus rule — at most 2^16 = 65,536 links per `ChannelSettle` and 2^17 = 131,072 steps per `ChannelOpen`, refused before any hashing; testnet-1: 2,007,000; `null` on a v0.19.6 binary, which does not answer the field at all). Operators read these off every seat before a height is named; a node that answers a different number is the one that will island.** |
| `hk_getValidators` | — | `count`, `total_power`, `validators[{address, voting_power, epoch, root_pk, genesis}]` — the set as of the tip; `epoch` climbs on every self-rotation; `pending_set_changes[]` (v0.14.0). **v0.18.0 (G1):** `founding_power` (the genesis seats' power), `external_power`, `quorum_power` (`2·total/3 + 1` — the smallest power strictly above ⅔), `max_absent_power` (`total − quorum`: how much power may be down before the chain stalls), `founders_alone_decide` (`3·founding > 2·total`), `bootstrap {height, founding_power, active}` (the activation table for this chain id — testnet-1: 110,000 / 4 — and whether the tip is past it), and `genesis: true` on each seat the genesis lists. `pending_set_changes[].change` and `hk_getBlock.set_changes[].change` read `admit`, `remove` or `set_power` |
| `hk_getMempool` | — | `count`, `txids[≤100]` — this node's pending admissions |
| `hk_getPeers` | — | **v0.15.2 (N1).** This node's live p2p peer table, straight from its swarm: `self{peer_id, version, genesis_digest}`, `count`, `inbound`, `outbound`, `public_addr` (peers on a public address), `identified` (identify received on the consensus protocol), `islands_refused` (peers on a different genesis disconnected by the genesis gate since boot), `peers[{peer_id, direction: inbound\|outbound, addr, private_addr, version, genesis: match\|untagged\|pending\|mismatch, identified, connected_secs, connections, last_connection_secs, reconnects}]`. **v0.19.3:** `last_connection_secs` = seconds since the LATEST connection to that peer was established and `reconnects` = connections established beyond the first while the entry lived — a peer that restarts and dials in before its old socket dies keeps its entry (it never hits 0 connections), so `connected_secs` alone hid such restarts. `addr` is the connection's real remote address masked by the node to its /24 (v4) or /48 (v6) — never what the peer claims to listen on; `private_addr` marks loopback / RFC 1918 / CGNAT / ULA peers (the founding fleet peers over its private network); `version` is `null` for a ≤ v0.15.1 peer (it advertises its genesis but not its version). An entry exists only while a connection is open. The gateway's table is the network's public roll call because every kit node bootstraps through it; a node that peers only with other operators is not visible there |

`fee.burned_micro` is the cumulative burn since genesis (in `C(Σ)` once nonzero); `history.disk_from` is the lowest height this node can serve from its block log (the gap-free suffix — R10 v2), `ram_window` the number of recent decided heights held in memory, `indexed_txs` the size of the node-local search index (since v0.16.0 it is restored from `index3.bin` on restart, so it is rarely 0), `retain_blocks` (v0.16.0) the node's `HK_RETAIN_BLOCKS` setting or null — a pruned node answers `hk_getBlock` below `disk_from` with `not found`; point explorers and auditors at an archive node such as the public endpoint.

## Blocks & history

| Method | Params | Result |
|---|---|---|
| `hk_getBlocks` | `before?` (height, exclusive), `limit?` (default 20, **max 50**) | `blocks[{height, time, tx_count, aggregate, rotations, value_id}]` newest-first, `earliest` (= `history.disk_from`), `latest` |
| `hk_getBlock` | `height` | `found`, `height`, `time`, `parent_app_hash`, `tx_count`, `txs[{txid, sender, nonce, kind, fields{…}, receipt}]`, `aggregate` (bool — one STARK covered the block's spends), `rotations` (count of rotation certificates applied at this height), `certificate{round, value_id, signatures}` |
| `hk_getTx` | `txid` | `found`, `txid`, `height`, `index`, `summary{txid, sender, nonce, kind, fields}`, `receipt` — via the node-local tx index; `found:false` until the index pass has reached that height after a restart |
| `hk_getAccountTxs` | `id`, `limit?` (default 25, **max 100**) | `id`, `total`, `txs[{txid, height, kind}]` newest-first — every envelope the account sent or was credited by |
| `hk_getReceipt` | `txid` | `found`, `detail` — the consensus receipt string (`ok: <n> event(s)` or `rejected: <rule>`), from a ring of the newest 4,096 receipts; older receipts come back through `hk_getTx.receipt` |

`kind` is one of `transfer`, `account_create`, `mandate_create`, `mandate_spend`, `mandate_revoke`, `channel_open`, `channel_settle`, `channel_refund`, `shield`, `shielded_spend`, and since v0.15.0 (X1) `asset_register`, `asset_mint`, `asset_burn`, `asset_freeze`, `asset_pause` (fields: asset, symbol/decimals/policy, to/amount, destination hex, account/frozen, paused). Refusal receipts an issuer policy produces read `rejected: asset paused`, `rejected: frozen by issuer`, `rejected: asset is not pool-eligible`, `rejected: sender is not the asset's issuer`, `rejected: asset policy forbids this (…)`. Transparent kinds expose sender, counterparty and amount in `fields` (this is the transparent skeleton by design); pool kinds expose only nullifier / commitments / the pool fee. `hk_getBlock`/`hk_getBlocks` answer `{"error":"persistence disabled on this node (HK_NO_PERSIST)"}` on a node started without a block log.

## Accounts & money

| Method | Params | Result |
|---|---|---|
| `hk_getAccount` | `id` | `found`, `nonce` (= the next ratchet index), `auth_commit` (the currently committed one-time key), `balances[{asset, symbol?, amount, frozen}]` (X1, v0.15.0: every non-zero transparent balance, by asset) |
| `hk_balance` | `id`, `asset` | `amount` (string, micro) |
| `hk_getAsset` | `asset` **or** `issuer` + `symbol` | X1 (v0.15.0): `found`, `asset{asset, symbol, decimals, issuer, policy{flags, mintable, freezable, pausable, pool_eligible}, supply, burned, circulating, held, conserved, paused, frozen_count, registered_at}` — `conserved` is the node's own I5' check (`held == circulating`); `asset_id` echoes the derived id when not found |
| `hk_getAssets` | — | X1: `count`, `fee_asset`, `assets[…]` (the whole registry, same shape) |
| `hk_submitTx` | `tx` (a `SignedTx` JSON object — the CLI and the wallet build these) | `accepted: true, txid` or `accepted: false, reason` (mempool admission mirrors the state machine's checks: nonce window, balance **including the 100-micro envelope fee**, duplicate nullifier, …); an accepted tx is also pushed to the node's gossip peers. **R18 (2026-10-08):** three payload refusals at the door, judged before the signature. Two mirror the consensus caps in the state machine's own receipt wording (the same string a `rejected:` receipt carries from `activations.payword_cap_from`) — `channel too long (N steps, max 131072)` (a `ChannelOpen` whose `max_steps` exceeds 2^17; refused by the tx's own bytes, before any hash) and `settle delta too large (D links past the highest settled step, max 65536 per settlement)` (a `ChannelSettle` more than 2^16 links past the channel's `highest_step_settled` on the answering node — `hk_getChannel` shows it; one lookup, no hash; settle in several txs, each advancing at most 65,536 links — two of them on a channel at the cap; on a channel the node does not know, `D` is the settle's `step` itself: its open may be pending ahead of it, and without the open the state machine refuses it in O(1) anyway). The third is admission wording, because no receipt ever carries it — `settle too costly to propose (L links from the tip, max 131072 per block until verification is incremental — settle in pieces)`: the verifier hashes `step` links from the tip, a proposer carries at most 2^17 of them per block, and a settle no block this node builds could carry is refused rather than parked (reachable only on a channel opened before the height with more than 2^17 steps — the cap keeps a post-height channel inside the budget). The door counts from the chain, not from a settle still pending in its pool: a second settle on the same channel more than a cap past the chain's step waits for the first to land. A settle on a known channel that is refunded, or at a step at/below the settled one or past `max_steps`, is left to the state machine, which refuses it in O(1) (and a proposer costs it nothing) |
| `hk_mandateAvailable` | `leaf` (mandate id), `at?` (unix seconds; default chain time) | `available` (string, micro) — what the leaf may spend right now under every ancestor's drip and cap, or `null` + `reason` |
| `hk_getChannel` | `id` | `payer`, `payee`, `asset`, `mandate`, `tip`, `unit_price`, `max_steps`, `highest_step_settled`, `escrow_remaining`, `expiry`, `refunded` — a PayWord channel's full state |

Every envelope pays the protocol fee (`docs/FEES.md`): a transfer of `amount` needs `amount + fee.micro` available; the receipt for a shortfall is `rejected: insufficient balance for the protocol fee (have <a>, need <b>)` (fee) or `rejected: insufficient balance: have <a>, need <b>` (payload after the fee was debited).

## Shielded pool

| Method | Params | Result |
|---|---|---|
| `hk_getPoolInfo` | `asset?` | `legacy` (bool), `version`, `asset`, `root` (current commitment-tree root), `latest_anchor`, `next_index`, `nullifiers` (count), `total_shielded` (string, micro — the pool's conservation ledger). **P6 (v0.19.0): one pool per asset** — `asset` (64-hex) selects that asset's pool; absent = the legacy pool (pinned to the first asset ever shielded), so pre-P6 clients keep working unchanged |
| `hk_getPools` | — | P6: `count`, `multi_pool_from` (the activation height; null = never), `pools[]` — every pool as `hk_getPoolInfo` reports it, the legacy one first |
| `hk_getPoolNotes` | `asset?` (P6: which pool; absent = legacy), `from?` (leaf index, default 0), `limit?` (default and cap 10,000) | `notes[{index, commitment, stealth_ct}]`, `from`, `count`, `total`, `next` — **paged since v0.16.1 (H3)**: `next` is the index the following page starts at, `null` when this page reached the end. A wallet keeps `next` as its scan cursor and asks only for what it has not trial-decrypted yet (the pool is append-only); a page of 10,000 notes is ≈24 MB of hex, so clients on slow links page smaller (the desktop wallet uses 2,000) |
| `hk_getPoolLeaves` | `asset?`, `from?`, `limit?` (same paging) | `leaves[hex…]`, `from`, `count`, `total`, `next` — the commitment list, for a client that insists on rebuilding paths itself |
| `hk_getPoolPath` | `asset?`, `index` | `index`, `commitment`, `siblings[32]` (bottom → top), `root`, `total` — **v0.16.1 (H3)**: one authentication path, so a spender never downloads the pool. The wallet re-folds the siblings and refuses a path that does not reach `root`; the proof binds that root, which the chain accepts only while it is a recent anchor — a wrong path from a node can cost the spender a rejected transaction, never a coin. `index` out of range → `error`; **v0.19.6 (R17 L-5):** at most 2 path builds in flight per node (the call copies every leaf of the pool and rebuilds the tree) — past that `{"error":"busy: 2 pool-path builds already in flight — retry in a moment"}` |
| `hk_nullifierSpent` | `asset?`, `nullifier` | `spent` (bool) — P6: in that asset's pool (absent = legacy) |
| `hk_submitBundle` | `txs[]` (proof-less pool txs), `agg_proof` (hex, one aggregate STARK) | `accepted`, `txids[]` — the aggregator path (P2.3): one proof for every spend in the bundle. **R18 review (2026-10-08):** a bundle may carry ONLY proof-less `shield` / `shielded_spend` txs (empty `proof` — the aggregate is their proof) and at most 1,024 of them; anything else is refused with `{"error":"bad txs: a bundle may carry only proof-less MintToPool / ShieldedSpend txs covered by its aggregate (tx N is not one — submit it through hk_submitTx)"}`. Before the review a bundle's txs rode ahead of the proposer's pool uncosted and unseen by the mempool's caps, so a `channel_settle` inside one reached an upgraded proposer's block without passing any R18 check |

## Operator

| Method | Params | Result |
|---|---|---|
| `hk_submitRotation` | `cert` (a root-signed `RotationCert`) | `accepted`, `epoch`, `queued` — queues a **foreign** validator's rotation certificate for this node's next proposal (the peer-carried revival path: `hk-node issue-rotation <HOME> <EPOCH>` produces the cert offline; any live node carries it in). **v0.19.6 (L-2):** the cert is judged by the chain's rotation rule at `height + 1` (the earliest block it can commit in), exactly as commit will judge it: before `activations.rotation_v2_from` the v1 certificate (no chain binding) as always; from it only a chain-bound v2 certificate — `hk-node issue-rotation <HOME> <EPOCH> <TIP+1> <CHAIN_ID>` — whose `valid_from_height` is not past the activation height (that commit + 1, i.e. `height + 2` at submit time) and not more than 100,000 blocks before it. **Submit it to the node you read the tip from (or one at least as far along):** the window is judged at the receiving node's own tip, so a node two or more blocks behind the peer that supplied `TIP+1` refuses the certificate as `past its activation height` although commit would accept it later. Refusals (`accepted: false, reason`): `signed under the v1 domain — …` (re-issue with the chain id), `valid_from_height N is past its activation height … (submit it to a node whose tip is at least the one it was issued against, or re-issue it at this node's tip)`, `stale — valid_from_height N is more than 100000 blocks before …`, `invalid or stale (… v2 domain, chain …)` (bad signature or signed for another chain). This is an operator method for a validator's own node or a peer it trusts over a firewalled RPC — not the public endpoint (see "Limits and refusals") |
| `hk_submitSetChange` | `cert` (a `SetChangeCert`: body + approvals) | `accepted`, `queued`, `approvals`, `window` — **V1 (v0.14):** queues a validator-set change (admit / remove one seat) approved by root signatures from strictly more than ⅔ of the current seats' voting power; re-verified at propose and at commit; effective one height after it commits. `hk-node set-change propose|approve|assemble` builds it (docs/V1-VALIDATOR-SET-CHANGES.md) |
| `hk_gossipTxs` | `txs[]` | `admitted`, `dropped` — peer ingress for transaction gossip (single hop: gossiped txs are admitted, never re-forwarded). Meant for validator-to-validator use over a firewalled RPC |

## Errors you will actually see

`unknown method: <name>` · `missing/invalid param: <name>` · `persistence disabled on this node (HK_NO_PERSIST)` · `rejected: …` receipts inside `hk_submitTx` results (the tx was *admitted or refused by the mempool*; a tx that is admitted but later refused in a block gets its `rejected:` string via `hk_getReceipt` / `hk_getTx`).

Since v0.15.2 `hk_getBlock` also returns `set_changes[{change: admit|remove|set_power (v0.18.0), root_pk, voting_power, approvals, not_before, not_after}]` and `hk_getBlocks` entries carry `set_changes` (count) — the validator-set change certificates a block carries (block 72219 on testnet-1 seated the first external validator).

## Limits and refusals (v0.13.2)

Per request: 10 s to arrive in full (`408 request timed out`), 8 MiB body (`413`), 256 concurrent connections per node (`503 rpc busy`). **R17 (2026-10-06, client-side):** `hk_submitRotation` and `hk_submitSetChange` run every free check (seat, epoch / window, chain id, approvals, queue dedup) *before* the SLH-DSA root-signature verify, verify with no lock held, and allow at most 2 verifies in flight per node — a caller past that gets `{"error":"busy: 2 root-signature verifications already in flight — retry in a moment"}` (HTTP 400) and retries; the pool feed (`hk_getPoolNotes` / `hk_getPoolLeaves` / `hk_getPoolPath`) is paged under its lock again (v0.19.0 cloned the whole feed per call), response shapes unchanged, and `hk_getPoolPath` — which still copies every leaf of the pool and builds the tree per call — allows at most 2 builds in flight per node (`{"error":"busy: 2 pool-path builds already in flight — retry in a moment"}`, HTTP 400; a wallet needs one path per spend). The 2-slot bounds protect the node's commit path, not the caller: on a PUBLIC endpoint a flood of well-shaped garbage keeps the two operator slots busy and a legitimate `hk_submitRotation` / `hk_submitSetChange` there answers `busy` — which is why the operator methods are submitted through a validator's own node (loopback RPC, firewalled to peers; the R2 revival procedure in `docs/VALIDATOR-ONBOARDING.md`) and the public gateway's reverse proxy rate-limits POSTs per source address (ops; the node cannot key on a client address behind a proxy). **R17 / L-2 (v0.19.6, consensus, gated by `activations.rotation_v2_from`):** `hk_submitRotation` refuses, for free, a v2-era certificate whose `valid_from_height` is outside its window, and after the verify a v1 certificate on a chain past its height (`signed under the v1 domain`) or a v2 certificate signed for another chain. **R18 (2026-10-08, client-side, no gate):** `hk_submitTx` and `hk_gossipTxs` refuse at the door a `ChannelOpen` whose `max_steps` exceeds 2^17 (before the envelope hashes — the tx's own bytes decide), a `ChannelSettle` more than 2^16 links past its channel's settled step (or, on a channel the node does not know, a `step` past 2^16), and a `ChannelSettle` that would make the chain hash more than 2^17 links — the proposer's per-block budget, so nothing admitted can sit in the pool unproposable (two lookups under the lock, before the account walk) — the three `hk_submitTx` reasons above. That settle cost every validator one SHAKE-256 per link at apply (up to ~4.29e9, synchronously, under the chain mutex), was free to its sender (refusals refund the fee and do not ratchet the nonce) and replayed every block; the consensus rule behind the two caps activates at `activations.payword_cap_from`. `hk_submitBundle` admits only proof-less pool txs (its row above) — the bundle rides a proposer's block ahead of its pool, so it is judged at submit. **Operator methods are not browser-callable:** `hk_submitRotation`, `hk_submitSetChange`, `hk_gossipTxs` and `hk_submitBundle` answer `403` when the request carries an `Origin` header (a web page cannot drive a node's operator surface even when it can reach it); every other method, including `hk_submitTx`, keeps CORS `*`. `hk_submitBundle` queues at most 64 bundles and refuses a duplicate aggregate; `hk_gossipTxs` takes at most 1,024 txs per call. Still ledgered (`docs/P3.2-IMPLEMENTATION-PLAN.md`): no auth, no per-client rate limit · `hk_getPoolNotes`/`hk_getPoolLeaves` are paged (≤ 10,000 per call) and `hk_getPoolPath` answers one path since v0.16.1 (H3) · `hk_getAccountTxs` turns any account id into its full transparent payment graph (by design of the transparent skeleton; shield if you need privacy).
