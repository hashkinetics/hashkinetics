## [0.17.0] — 2026-09-06 — 🪶 R11: the node verifies with a verify-only SP1 client — seconds to start, a resident set a stranger's box can carry (client-only; wallet stays v0.14.1)
- **The one line (`hk-node/src/verifier.rs`).** `ProverClient::builder().cpu().build()` → `ProverClient::builder().light().build()`. Since the first shielded block the node had built SP1's FULL CPU prover to call `verify`: the recursion programs for every shard shape, the shrink and wrap provers — the whole proving engine, at every start. On the fleet's 2-vCPU hosts that was **3–6 minutes** from `systemctl start` to an answering RPC and a **~6.7 GB** resident set that never produced a proof (INCIDENTS #6; the "8 GB minimum, 16 GB comfortable" line). sp1-sdk 6.4.0's `LightProver` builds the verifier machines and carries the pinned recursion-vk root; `prove` on it is an error by design. Verification is the SAME code path (`SP1Verifier` through `SP1NodeCore`) with the same embedded vk root — the SDK asserts the light and full clients agree in its own tests — so the accept set and the refuse set are unchanged: client-only, no consensus impact. The node never had a reason to prove; now it cannot. The binary shrank with it — **70.1 MB → 30.6 MB unpacked (24.6 MB → 9.8 MB gzipped)**: the proving engine, its recursion artifacts (`vk_map`) and the shrink/wrap provers are no longer linked at all, because nothing in the node references them (checked with `strings`: `SP1ProverEngine`, `vk_map`, `wrap_prover`, "initializing cpu prover" are absent from v0.17.0; the light-client line is present).

## [0.16.1] — 2026-09-06 — 📜 H3: a paged pool feed, one-path spends, an incremental wallet scan (client-only; wallet v0.14.1)
- **H3 — `hk_getPoolNotes` / `hk_getPoolLeaves` are paged (`rpc.rs`).** `{from?, limit?}` → `{…, from, count, total, next}`; `limit` defaults to and is capped at **10,000** (`POOL_PAGE_MAX`, ≈24 MB of hex — bounded on the node whatever the pool grows to); `next` is the index the following page starts at, `null` at the end. A pre-H3 client that sends `{}` still gets the first 10,000 — the whole pool for a long time yet. Unit test `h3_pool_pages_are_bounded_and_chain_to_the_end`.
- **`hk_getPoolPath {index}` (new).** `{index, commitment, siblings[32], root, total}` from the node's leaf list (`hk_state::pool::full_tree_path`): a spender fetches ONE authentication path instead of every commitment. Trust boundary, plainly: the wallet re-folds the siblings and refuses a path that does not reach the stated root (`hk_wallet::fold_path`, `build_spend_with_path`, `build_disclosure_with_path` — unit-tested byte-identical to the leaf-list builders and refusing a bad root / wrong index / short path); the proof binds that root and the chain accepts it only while it is a recent anchor, so a lying node can cost a rejected tx, never a coin. `hk-node pool-path <RPC> <INDEX>` is the one-line diagnostic (folds locally, compares with `hk_getPoolInfo.root`).
- **Wallet v0.14.1 — incremental scan (`hk-wallet-gui/src/shielded.rs`).** `shield.json` gains a `scan` cache (`chain_id`, `scanned_through`, `notes[]` with value/rho/rcm/memo/spent) — sealed with the file when the wallet is protected, serde-defaulted for older files (one full scan, then remembered). Shield/unshield/pay/disclose build from the cache + `hk_getPoolPath` (fallback to a paged `hk_getPoolLeaves` on a pre-H3 node). The ACTIVITY line says how many new entries a scan read.

## [0.16.0] — 2026-09-05 — 🗄️🔐 S+K: storage that stops growing in the wrong places, keys that can live sealed — block-log segments + retention, persisted search index, snapshot knobs; `HKE1` sealed key files (validator seed, account/wallet files, GUI), faucet hot/cold + low-watermark (client-only; no consensus change, no activation; wallet v0.14.0)
- **C2.8 — block-log segments (`store.rs`).** Committed blocks keep landing as one file per height (atomic, crash-safe — the hot tail); at snapshot time, every completed run of 1,024 heights at-or-below the snapshot is packed off the commit path into `blocks/seg<id:09>.hkb` (`"HKS1" | frames(u32 len + bincode StoredBlock) | index[1024] u64 offsets (0 = absent) | u64 index_offset | "HKS1"`, tmp → fsync → rename, then the per-height files go). Readers try the per-height file first, then the segment; a segment is written before anything is deleted, so a reader never sees a gap. One compaction at a time (a lock); a node upgraded from ≤ v0.15 packs its history in a background `hk-compact` thread on first start (`HK_COMPACT_HISTORY=0` skips it). testnet-1 at height ~76k: ~76,000 files → ~74 segments + the tail. Unit tests: roundtrip + idempotence, retention on whole segments only.
- **Retention (`HK_RETAIN_BLOCKS=N`)** deletes whole segments older than `tip − N` — never the hot tail, never a partial segment; the servable floor (`hk_chainInfo.history.disk_from`) moves up and `history.retain_blocks` says N (null on an archive node). Voters and the public gateway keep everything; the knob exists for observers and for the day a disk is small.
- **S2 — persisted search index (`index3.bin`).** The tx and account indexes (`PersistedIndex{through_height, tx[], acct[]}`) are written at snapshot time and every `HK_INDEX_PERSIST_EVERY` blocks; a restart loads them and resumes the index pass **above** `through_height` instead of re-reading every block file (the `index_floor` marks what is still being back-filled; `u64::MAX` once the history pass is done). Log: `search index persisted (S2)` / `search index restored from disk (S2) — resuming above it`.
- **S3 — snapshot knobs.** `HK_KEEP_PREV_SNAPSHOT=1` keeps `snapshot3.prev.bin` (an operator's escape hatch if the newest image ever fails its commitment check); `HK_SNAPSHOT_EVERY` (existing), `HK_INDEX_PERSIST_EVERY`, `HK_COMPACT_HISTORY` — all documented in `docs/VALIDATOR-ONBOARDING.md` §5b.
- **K1/K2 — keys at rest (`hk-wallet/src/sealed.rs`, `hk-node/src/keys.rs`).** One envelope for every secret file: `HKE1` = Argon2id → XChaCha20-Poly1305, AAD `hk/v1/sealed`, one salt per key and a fresh nonce per write, a JSON envelope that says what it is (`hke, kdf, m_kib, t, p, salt, nonce, ct[, kf]`) and reveals nothing else. Plain files keep working — the loaders sniff the envelope, never ask for anything on a plain file. Passphrase sources, first hit wins: `<PREFIX>_PASSPHRASE` → `<PREFIX>_PASSPHRASE_FILE` (first line) → systemd `$CREDENTIALS_DIRECTORY/<credential>` (`LoadCredential=`) → a no-echo prompt when stdin is a terminal; otherwise a loud refusal (`this file is sealed — set …`) rather than a half-armed node. A wrong passphrase fails the AEAD tag — no partial decrypt, a clean `wrong … passphrase` error.
  - **Hardened against offline guessing (the question "is it brute-force hardened?", answered with the QE-Vault profile brought to a size a validator host can afford):** default **Argon2id 512 MiB × 4 passes × 4 lanes (≈1 s)** — memory-hard, so a 24 GB GPU fits ~48 guesses at a time and manages tens of guesses per second, not billions; parameters ride in the envelope (`HK_SEAL_M_KIB` / `HK_SEAL_T` for new seals, floor 64 MiB / t=3). **The KDF runs once per unlock**, the derived key is cached per salt (`SealKey`), so reserve-then-sign re-seals are an AEAD call — a heavy KDF costs nothing per send. **Passphrases are checked, not trusted** (`check_strength`: ≥ 12 characters or a 4+-word phrase; common words with decoration, keyboard walks, repeats and digit runs refused; `HK_SEAL_ALLOW_WEAK=1` only for devnets); `hk-node passphrase-new` and the GUI's *generate* print 7 words from a 512-word list (63 bits — millions of GPU-years at this cost). **Optional key file, a second factor:** `hk-node keyfile-new PATH` + `HK_KEY_KEYFILE` / `HK_WALLET_KEYFILE` mix 32 random bytes into the key; the envelope names the file's fingerprint (`kf`), and without the file the passphrase opens nothing — brute force becomes impossible rather than slow. Post-quantum note: a 256-bit symmetric key under Argon2id is already quantum-safe; no lattice KEM is needed for a local file.
  - **K2 validator seed:** `hk-node key-seal | key-unseal <HOME>` on `priv_validator_key.json` (prefix `HK_KEY`, credential `hk-key-passphrase`); `start`, `issue-rotation`, `set-change approve` read the sealed file; `keygen` seals from the first byte when `HK_KEY_PASSPHRASE` is exported. Onboarding §5a + the unit's `LoadCredential=hk-key-passphrase:/etc/hk/key-passphrase`. Honest scope: a running node holds the seed in memory, and `consensus_state.bin` (the live LMS tree state, rewritten per vote) stays plain in this release — the current operational tree only; a root-signed rotation retires it. `docs/MAINNET-KEY-MANAGEMENT.md` names the HSM seam (`HashSigner::sign` / `RootSecret::sign`) this plugs into.
  - **K1 wallet files:** `hk-node account-seal | account-unseal <DIR>` seals `account.json` + `wallet.json` (+ `shield.json`) under one passphrase and one salt (prefix `HK_WALLET`, credential `hk-wallet-passphrase`); `account-*`, `wallet …`, `asset …` and `faucet-serve` read them; reserve-then-sign re-seals on every save with the cached key (microseconds). Secret files are written tmp → fsync → rename, mode 0600 on Unix.
  - **Wallet v0.14.0 (GUI):** *Backup & advanced → Protect with a passphrase* seals `account.json` and `shield.json` with the same envelope (CLI and GUI still share a wallet); the same strength rule, a *generate* button (7 words, shown once, copy), `HK_WALLET_KEYFILE` honoured; a sealed wallet opens to an **Unlock** screen (≈1 s, once) instead of offering to create a wallet over it; change / remove passphrase re-writes both files only after reading them back under the old one; the derived key lives in memory for the session. `docs/WALLET-GUIDE.md` §5a.
- **K3 — faucet hot/cold + low-watermark (`faucet.rs`, `docs/FAUCET-RUNBOOK.md`).** The faucet is now run as a hot wallet with a small float, refilled by `account-send` from a cold treasury that never sits on the faucet host (two accounts, two signers — the "stop the faucet before a treasury send" rule is gone). `/health` gains `low` (balance < `HK_FAUCET_LOW_MICRO` / `--low-micro`, default 50 drips), `low_watermark_micro`, `reserve_micro`, `drips_left`; below `HK_FAUCET_RESERVE_MICRO` (default 2 drips) a drip is answered **503 "faucet is being refilled"** before any nonce is reserved — no ratchet index is burned on a transfer the chain would refuse. Startup and every low drip log the refill warning.

## [0.15.2] — 2026-09-05 — 📡 N1: the live peer table — `hk_getPeers`, `node_version`, peers advertise their version; the /network page shows who is on testnet-1 in real time (client-only; no consensus change, no activation)
- **Asked for as "something live on the website that scans how many external nodes there are"; built as a measurement, not a proxy.** The node's own swarm loop learns everything worth showing — who is connected, which way, from which address, on which genesis, on which version — so the vendored network crate now keeps a process-wide **peer table** (`HkPeer`: peer id, `inbound|outbound`, the connection's real remote address, identify status, genesis tag, node version, connected-since, live connection count), updated on `ConnectionEstablished`, on identify (consensus protocol, after the genesis gate) and on `ConnectionClosed` (the entry is removed when the last connection goes). An entry exists only while a socket is open: joins appear, leaves vanish, nothing is configured.
- **`hk_getPeers`** (read-only, browser-callable): `self{peer_id, version, genesis_digest}`, `count`, `inbound`, `outbound`, `public_addr`, `identified`, `islands_refused`, `peers[…]`. The node masks addresses itself — /24 for v4, /48 for v6 (v4-mapped v6 masked like v4), DNS kept — and flags `private_addr` (loopback / RFC 1918 / CGNAT / ULA: the founding fleet peers over its private network). `hk_chainInfo` gains `node_version` (the v0.14.1 nit: operators can finally prove which binary answers) and `peers`.
- **Version tag.** identify's `agent_version` becomes `hashkinetics/1/genesis/<64 hex>/hk-node/<version>`. ## [0.10.10] — 2026-09-01 — 🛡️ R8 + R1.b: a validator can nap without eating its keychain
Built for the external-validator era: strangers' nodes WILL go offline, fall behind, and wedge — ours only survived because we babysat them. Two shipped fixes make a parked validator boring instead of fatal.
### The gate (devnet, 2026-09-01 — the val-0 scenario, reproduced and cured)
- A voter was wedged below tip with value-sync disabled: it spent **2 leaves** (one round, before peer evidence arrived), then went silent — claim path confirmed live (`532` future-height votes recorded from all 3 distinct peers; core-consensus buffers them at exactly the instrumented ingress).
- Sync restored: it climbed **850 heights in ~70 s** while R8 suppressed every futile vote attempt en route (9× `R8: behind the network — abstaining … height=12 peer_tip=Some(830)`), landed **byte-identical** with the fleet (`app_hash c59d0effa184cb68` at h=862, 5 ms apart), and cast a live Prevote at **h=863** — the first possible height.
- The leaf ledger: the wedged voter finished at **69 used vs 2,358–2,566** on its peers — ~39 spent total (stuck round + live voting after rejoin), versus ~1,700 that pre-R8 catch-up voting would have burned. Forensics closed en route: rebroadcast re-sends stored votes (never re-signs, free), a truly-stuck driver is protocol-quiescent (~2 leaves per event), and the historical 32,768-leaf burn is now fully attributed to catch-up voting — the exact path R8 gates.
### Fixed
- **R8 — abstain-while-behind: futile votes no longer burn one-time leaves.** A validator wedged below the network tip used to cycle consensus rounds at its stale height — every nil prevote/precommit spending an irreplaceable LMS leaf (a fresh 32,768-leaf tree burned to ZERO in ~20 h of exactly this). New `Context::abstain_threshold()` (default `None` = upstream unchanged — the same pattern as `validator_set_at` and `placeholder_signature`): when corroborated peer evidence puts the network ≥ gap heights ahead, the driver skips all three leaf-spending arms (vote signing, proposal signing, value building). Abstaining is indistinguishable from being offline, which BFT already tolerates. The signal: future-height votes/proposals (already buffered by core-consensus) record per-validator height claims — **only current-set members count** (spam-proof), and the trigger is the **second-highest claim among distinct validators**, so one faulty validator can't fire it and a lone ahead-of-quorum node can't stall the majority. Default 20-height gap (`HK_ABSTAIN_GAP` overrides, `=0` disables). Ledgered residual: a same-height stall (quorum-loss halt) still spends leaves on live rounds — those rounds could actually commit, and the burn decays with round-timeout backoff.
- **R1.b — rotation threshold now evaluated on a tick, not only on commit.** The leaf-budget check lived in the commit path — a node that never commits (parked, minority partition: exactly the node whose leaves are draining) NEVER evaluated it, and burned to zero with the threshold armed. A 60 s tick (observers no-op) reads the live gauge, runs the SAME `rotation_due` (threshold clause only — unit-tested shape), and on due issues the root-signed cert **out-of-band**: self-enqueued into the foreign-cert queue AND pushed to every gossip peer via `hk_submitRotation` — the peer-carried revival path, self-served before exhaustion instead of human-driven after it. Epoch-monotone acceptors make duplicate issuance harmless by construction.
### Together
R8 preserves the leaves; R1.b spends the preserved leaves on a rotation cert while they still exist. The incident pattern (parked → burned → dead → human revival) becomes: parked → silent → self-rotated → rejoins. ## [0.10.8] — 2026-08-31 — ⚡ R5.2: PARALLEL VERIFICATION — the join kit learns to outrun the chain
The observer-from-genesis receipt exposed the truth: catch-up collapsed to ~2 blocks/min against a chain adding ~27/min — a joiner that can never converge. Recon found the floor was never one thing:
### Fixed
- **Duplicate certificate verification eliminated.** Every SYNCED block verified its commit certificate twice — once on the sync path, again on the decide path, same certificate. `State.last_verified_certificate` (height, round, value-id) memoizes the sync-path pass; `decide` skips the re-verify on match. Live decides never set the memo and verify exactly as before. Half the hash-based signature work per synced block, ~15 lines.
- **One state-commitment walk per block, not two.** The post-apply `state_commitment()` (log line) and the next block's parent-hash check recomputed the SAME value — each an O(entire state, every nullifier ever) walk that GROWS with height (this, not constant-cost crypto, is why the observer's rate decayed). The post-apply hash is now cached and consumed by the next parent check; any error path drops the cache and recomputes honestly.
### Added
- **Batch signature verification hook** (`SigningProvider::verify_signed_votes_batch`, default `None` = serial fallback — same shape as R6's `validator_set_at`). The blanket `verify_commit_certificate` does one cheap ordered pass (duplicates, set membership, precommit reconstruction), then hands ALL LMS/HSS verifies to the provider's fast path. `HkSigningProvider` runs them on a dedicated **32 MiB-stack rayon pool** (`hk-consensus::par` — hbs-lms overflows default 2 MiB workers; capped at 8 threads). Boxed providers delegate, so the engine's `Box<dyn SigningProvider>` keeps the override.
- **Parallel envelope pre-verification.** A fat load-test-era block paid thousands of Lamport verifies serially INSIDE the state lock. The pure part (signing digest + Lamport over the tx's own fields) now runs `par_bools` outside the lock; `apply_block_verified` consumes the verdicts with check order IDENTICAL to the inline path (account → nonce → auth-commit → signature), so the success set is byte-for-byte unchanged whichever path a node takes. The key→account binding stays ordered.
- **Apply-cost telemetry** — `R5.2 apply-cost window` log every 100 blocks: pre/agg/apply/hash/save/snap ms. The 450 ms/block floor was an inference; now every node measures its own.
- **`HK_SNAPSHOT_EVERY`** env (default 16): the full-image snapshot + fsync grows with state and taxes catch-up; a grinding observer can widen the cadence (crash cost = replaying a few more blocks).
### Deliberately unchanged
- Engine-level batch pre-verify of whole sync batches (20-way across certificates) parked as **R5.2b** — measure first; the per-block wins may already clear the ~27 blk/min convergence bar.
### Proven in production, same day
- **Observer hot-swapped to v0.10.8** (e2-standard-8): sustained **71 blocks/min** measured over 2 minutes (was ~2 blk/min — 35×), net +44 blk/min against the live chain. Telemetry window at the early era: `pre=0 agg=0 apply=0 hash=0 save_ms≈3.2/blk` — after R5.2 the measured bottleneck is the per-block fsync, not crypto.
- **New failure mode found and fixed operationally: observer signer exhaustion.** A syncing non-validator SELF-SIGNS each synced proposal to drive the state machine (~1 LMS leaf/block; wedge-loops burn far more) — the original observer silently spent its ENTIRE 32,768-leaf tree (state file read `used = 0x8000` exactly), and every later sync value died as `Unexpected resume: Continue, expected Resume::SignedProposal`. Non-validators have no on-chain revival (their root isn't in the set), but their self-signatures are consumed only locally — so the remedy is: stop, rotate the spent `consensus_state.bin` aside, start (fresh tree). An **unwedge watchdog** (systemd timer, 2-min cadence) now does this automatically; the tree covers ~30k blocks per cycle. Proper fix parked as **R5.4: a syncing non-validator should not spend hash-based leaves at all** (accept sync values without self-signing, and let a failed SignProposal degrade gracefully instead of erroring the message).

## [0.10.7] — 2026-08-30 — 🧠 R6: PER-HEIGHT VALIDATOR-SET VERIFICATION — the chain remembers who signed what
### Added
- **Commit certificates now verify against the validator set AS OF their height** (the set that actually signed them), not the current set. `Context::validator_set_at(height)` (default `None` = old behavior) + the engine's `VerifyCommitCertificate` handler swaps in the historical set keyed by `certificate.height` — one interception point fixes both the sync and decide paths, no wire changes. `HkContext` answers from a shared **set history** (`(effective_from_height, set)`), seeded at genesis, reseeded at snapshot restore, appended on every committed rotation (live and replay).
- **`decide.rs` de-panicked:** a certificate failing verification used to `assert!` → kill the consensus actor → poison the shared validator mutex → half-dead node with a live RPC (the exact production corpse pose, twice). It now returns `InvalidCommitCertificate` with an error log; all `validators.lock()` sites recover poisoned guards.
### Proven in production, same day
- **val-0's THIRD revival:** E3 rotation cert issued offline + carried by a peer (`hk_submitRotation`), store transplant, then **organic sync across live rotation boundaries (E44/E7/E8) → adopted the fresh E3 tree mid-sync → voting. True 4/4 at 50,443+.**
- **Observer-from-genesis receipt (in progress):** a brand-new VM joined via `networks/staging-1` (public seed DNS, published fingerprint verified: `557f2ea6c…`), reports `chain_id: hashkinetics-1-557f2ea6`, and is re-verifying the entire chain from block 1 — every rotation boundary, every STARK.

## [0.10.6] — 2026-08-30 — 🪪 THE IDENTITY RELEASE — chain_id bound to genesis; islands refused
